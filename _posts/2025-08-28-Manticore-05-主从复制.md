## 主从复制

Manticore 的复制由 Galera 库提供支持，并拥有几个令人印象深刻的功能：

- 真正的多主：随时读取和写入任何节点。
- 几乎同步复制，没有从机延迟，节点崩溃后没有数据丢失。
- 热备用：故障转移期间没有停机时间（因为没有故障转移）。
- 紧密耦合：所有节点保持相同的状态，节点之间不允许有分歧的数据。
- 自动节点配置：无需手动备份数据库并在新节点上恢复。
- 易于使用和部署。
- 检测和自动驱逐不可靠的节点。
- 基于认证的复制。

主从复制在分区表的情况下一样有效，分布式表也可以是复制过程的一部分。复制是多主节点的，因此同时写入任何节点或多个节点也同样有效。

### 几个重要概念，必不可少

- name: 此选项指定集群的名称。它应该在系统中的所有集群中是唯一的。
> 注： JOIN 命令允许的最大主机名长度为 253 个字符。如果超过此限制，searchd 将生成错误。

- path: 选项指定写集缓存复制和来自其他节点的传入表的数据目录。此值在系统中的所有集群中应是唯一的，并且应指定为 data_dir目录的相对路径。默认情况下，它设置为 data_dir 的值。

- nodes: 选项是集群中所有节点的地址：端口对列表，用逗号分隔。此列表应使用节点的 API 接口获取，并且还可以包含当前节点的地址。它用于将节点加入集群并在重新启动后重新加入集群。

- options: 选项选项允许您将其他选项直接传递给Galera复制插件

- configuration > listen: 必须指定listen，其中包含其他节点可访问的 IP 地址或具有可访问 IP 地址的node_address。
  
- configuration > listen:xxxx-xxxx:replication 如果没有设置复制监听指令，则 Manticore 将使用每个创建的集群的默认协议监听端口之后的 200 个端口范围内的前两个空闲端口。Manticore 不会立即开始监听这些端口。相反，只有在您开始使用复制时，它才会从指定范围内随机获取可用端口。

- configuration > data_dir: 必须在配置文件的“searchd”部分设置data_dir选项

- configuration > server_id: 您可以为每个集群节点上的server_id设置唯一值。如果未设置值，节点将尝试使用 MAC 地址或随机数来生成server_id。

```bash
searchd {
  listen   = 9312
  listen   = 192.168.1.101:9360-9370:replication
  data_dir = /var/lib/manticore/
  ...
 }
```

## 配置一个集群

### **最小初始化一个集群**

```sql
CREATE CLUSTER test
```

### **给集群添加需要复制的表**

```sql
ALTER CLUSTER test ADD t1
ALTER CLUSTER test ADD t2
```

MySQL client连接，确认集群情况：

```sql
mysql> show status;

| cluster_test_state_uuid                 | df11589c-84a7-11f0-8e04-422e81761315                                                                                                                         |
| cluster_test_conf_id                    | 2                                                                                                                                                            |
| cluster_test_status                     | primary                                                                                                                                                      |
| cluster_test_size                       | 2                                                                                                                                                            |
| cluster_test_local_index                | 1                                                                                                                                                            |
| cluster_test_node_state                 | synced                                                                                                                                                       |

| cluster_test_nodes_view                 | 192.168.0.5:9312,192.168.0.5:9424:replication,192.168.0.6:9312,192.168.0.6:9422:replication                                                          |
| cluster_test_indexes_count              | 1                                                                                                                                                            |
| cluster_test_indexes                    | t1,t2    
```

### **新节点加入集群**

```sql
JOIN CLUSTER test AT '192.168.0.6:9312'
```

### **集群写操作**

INSERT, REPLACE, DELETE, TRUNCATE, UPDATE 需要指定集群名称

```sql
INSERT INTO test:t1 VALUES ( 'claire female' )
TRUNCATE RTINDEX test:t1
UPDATE INTO test:t1 SET age=20 WHERE MATCH ('claire') AND id IN (1,101,201)
DELETE FROM test:t1 WHERE MATCH ('dumy') AND id>1
```

### **集群读操作**

就和正常非复制表一样查询即可，不需要集群名称前缀，你加了前缀也会忽视，即你写了一个错误的集群名称也同样可以查到指定表的数据

```sql
SELECT * FROM t1
SELECT * FROM test:t1
SELECT * FROM test2:t1
```

### **集群去除一张复制表**

```sql
ALTER CLUSTER test DROP t1
```

### **集群去除一个节点**

停止节点，然后刷新节点信息

```sql
ALTER CLUSTER test UPDATE nodes 
```

### **删除一个集群**

```sql
DELETE CLUSTER test
```

## 集群的重启与恢复

详细拆解Manticore Search**集群重启与恢复**的核心逻辑、操作步骤及异常处理方案。其中**集群重启**是 **“恢复” **的基础操作子集。

grastate.dat（存储于集群路径）是两者共同的 “核心凭证文件”，其记录的safe_to_bootstrap（引导资格）和seqno（事务序列号）是操作决策的核心依据

若将 **“集群重启”** 视为 “从‘停机状态’到‘运行状态’的启动动作集合”，则“**集群恢复**” 是 “从‘故障状态’（如部分节点离线、脑裂、非主状态）到‘正常状态’的完整修复过程”。两者的差异主要体现在**场景范围、操作目标、核心手段、风险点**四个维度

**集群重启**的核心手段是 “启动参数控制”（如--new-cluster、--new-cluster-force），而**集群恢复**在此基础上，新增了 “SQL/JSON 命令修复异常状态”

### 官方说明

官方对于如何**集群重启**给出了操作方案，`--new-cluster` 和 `safe_to_bootstrap=1` 缺一不可，具体可参看[官方说明](https://manual.manticoresearch.com/Creating_a_cluster/Setting_up_replication/Restarting_a_cluster?r=1)

官方对于**集群恢复**，给出了6个case场景描述，有可以对号入座的也可以[直接参考](https://manual.manticoresearch.com/Creating_a_cluster/Setting_up_replication/Cluster_recovery?r=1)：

1. 单节点离线恢复（Case1）
2. 多节点离线、1节点存活（Case2）
3. 全集群正常停机恢复（Case3，与重启场景2一致）
4. 单节点崩溃后恢复（Case4）
5. 多节点离线导致集群非主状态（Case5）
6. 全集群崩溃恢复（Case6，与重启场景3一致）
7. 脑裂故障（Case7）

### 集群重启与恢复的场景对比

集群重启的场景仅覆盖“节点停机”相关场景，而集群恢复覆盖更广泛的“故障场景”，具体对比如下：

| 维度                | 集群重启                       | 集群恢复                         |
|---------------------|---------------------------------------------|---------------------------------------------|
| 核心场景            | 1. 单节点重启/临时断连（集群未全停）<br>2. 全集群正常关机后重启<br>3. 全集群异常崩溃后重启 | 1. 单节点离线恢复（Case1）<br>2. 多节点离线、1节点存活（Case2）<br>3. 全集群正常停机恢复（Case3，与重启场景2一致）<br>4. 单节点崩溃后恢复（Case4）<br>5. 多节点离线导致集群非主状态（Case5）<br>6. 全集群崩溃恢复（Case6，与重启场景3一致）<br>7. 脑裂故障（Case7） |
| 场景本质            | 仅处理“停机→启动”的状态转换                 | 处理“停机→启动”+“故障→修复”（如非主状态激活、脑裂修复） |
| 节点状态前提        | 启动前节点均为“停机状态”                    | 启动前可能存在“部分节点运行、部分离线”“所有节点运行但非主状态”等复杂情况 |

**关键举例**：  
- 若集群3个节点中A、B离线，C存活但因“节点数<总节点数的1/2”进入非主状态（Case5），此时C已处于“运行状态”，无需“重启”，需通过`SET CLUSTER ... pc.bootstrap=1`激活主状态——这是“恢复”独有的场景，重启无法覆盖。

### 集群重启与恢复的目标对比

- **集群重启的目标**：仅需确保“所有节点成功启动并加入集群”，不涉及集群运行中的状态修复。  
  例如：全集群正常关机后，通过`--new-cluster`启动参考节点，再启动其他节点，目标是“让集群跑起来”。

- **集群恢复的目标**：不仅要“让节点跑起来”，更要“修复集群的异常状态（如非主、脑裂），确保能处理写事务”。  
  例如：Case5中，C节点已运行但拒绝写事务，恢复的目标是“激活C的主组件，让其重新接受写请求”；Case7中，脑裂导致两组节点均拒绝写事务，恢复的目标是“让其中一组激活主组件，避免形成两个集群”。

### 集群重启与恢复的核心手段对比

集群重启的核心手段是“启动参数控制”（如`--new-cluster`、`--new-cluster-force`），而集群恢复在此基础上，新增了“SQL/JSON命令修复异常状态”，具体对比如下：

| 操作类型            | 集群重启核心手段                  | 集群恢复核心手段                  |
|---------------------|---------------------------------------------|---------------------------------------------|
| 引导主组件          | 1. `--new-cluster`（正常全停场景）<br>2. `--new-cluster-force`（崩溃场景）<br>3. systemd命令：`manticore_new_cluster`/`manticore_new_cluster --force` | 1. 同重启的引导手段（Case3、Case6）<br>2. **新增**：`SET CLUSTER [集群名] GLOBAL 'pc.bootstrap' = 1`（SQL/JSON命令，用于Case5非主状态激活、Case7脑裂修复） |
| 节点同步            | 依赖IST/SST自动同步                         | 依赖IST/SST自动同步（所有节点归队场景）      |
| 故障修复            | 无额外手段（仅处理启动）                    | 针对脑裂：仅在一组节点执行`pc.bootstrap`，避免双集群；针对非主状态：确认其他节点不可达后执行`pc.bootstrap` |

**关键差异点**：  
`SET CLUSTER ... pc.bootstrap=1`是恢复独有的核心命令，用于“在运行中的节点上激活主组件”，而重启场景中无需该命令——因为重启时节点均为停机状态，通过启动参数即可定义主组件。  


### 集群重启与恢复的风险对比

集群重启的风险集中在“参考节点选择错误”，而集群恢复的风险更复杂，需额外防范“脑裂导致的双集群”：

| 风险类型            | 集群重启                         | 集群恢复                         |
|---------------------|---------------------------------------------|---------------------------------------------|
| 核心风险            | 1. 正常全停场景：未先启动“最后停机节点”，导致节点启动报错<br>2. 崩溃场景：误选`seqno`小的节点用`--new-cluster-force`，覆盖最新数据 | 1. 同重启的风险（Case3、Case6）<br>2. **新增**：Case5/Case7中，未确认其他节点不可达就执行`pc.bootstrap`，导致脑裂后形成两个独立集群（数据无法合并）<br>3. Case7中，在两组脑裂节点均执行`pc.bootstrap`，直接形成双集群 |
| 风险防范手段        | 1. 启动前检查`grastate.dat`的`safe_to_bootstrap`和`seqno`<br>2. 严格按“最后停机节点优先”“`seqno`最大优先”启动 | 1. 同重启的防范手段<br>2. 执行`pc.bootstrap`前，通过日志、网络工具确认其他节点“完全不可达”<br>3. 脑裂修复时，仅在“数据更完整的一组节点”执行`pc.bootstrap` |


在Manticore Search集群运维中，若仅需“启动停机的节点”（无论单节点还是全集群），按“集群重启”的步骤操作；若集群已存在“非主状态”“脑裂”“部分节点运行但拒绝写事务”等故障，需按“集群恢复”的场景匹配对应手段（如`pc.bootstrap`）
