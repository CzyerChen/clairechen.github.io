## 组件介绍

Apache Doris 是一款基于 MPP（大规模并行处理）架构的高性能实时分析型数据库，其核心优势在于亚秒级查询响应、高并发处理能力以及对复杂分析场景的支持

1. 实时分析与高并发报表
场景特点
Doris 支持每秒数万次查询（QPS）的并发处理能力，且延迟控制在毫秒到亚秒级，尤其适合需要实时反馈的业务场景。例如：

实时看板（Dashboards）：企业内部分析师或管理者可通过实时更新的数据看板监控业务动态12。

客户侧高并发分析：如电商广告报表、网站主站点分析等。京东在广告报表中应用 Doris，每天写入 100 亿行数据，支撑上万 QPS，99 分位查询延迟仅 150ms147。

2. 即席查询（Ad-hoc Query）
场景特点
面向分析师的自助式灵活查询，无需预定义查询模式。例如：

小米基于 Doris 构建增长分析平台（GA），每天处理数万条 SQL 查询，平均延迟 10 秒，95 分位延迟低于 30 秒135。

支持复杂 SQL 查询和多表关联分析，适用于数据探索与临时分析需求68。

3. 统一数仓构建
场景特点
简化传统大数据架构，替代多组件（如 Spark、Hive、HBase 等）的复杂组合：

海底捞通过 Doris 重构数仓架构，显著降低运维复杂度，提升查询效率247。

支持 PB 级数据存储，结合列式存储和高效压缩技术，优化资源利用率38。

4. 数据湖联邦查询
场景特点
通过外部表直接查询 Hive、Iceberg、Hudi 等数据湖中的数据，无需数据迁移：

提升跨数据源查询性能，减少数据冗余135。

支持混合分析场景，例如结合实时数仓与离线湖仓的数据78。

5. 日志分析与检索
场景特点
Doris 2.0 引入倒排索引和全文检索功能，适用于大规模日志处理：

高效存储与查询日志数据，相比传统方案（如 Elasticsearch）成本降低 10 倍28。

应用于系统故障排查、安全监控等场景78。

6. 用户行为分析与个性化推荐
场景特点
处理海量用户行为数据，支持用户画像构建与实时推荐：

快手利用 Doris 分析用户行为数据，优化推荐算法，提升用户粘性7。

字节跳动在广告推荐系统中处理千亿级点击数据，提升精准度7。

7. 物联网（IoT）与实时监控
场景特点
实时处理设备数据流，支持预测性维护与设备状态监控：

美团通过 Doris 实时统计外卖订单数据，辅助运营决策7。

腾讯应用于游戏日志分析，实时监控玩家行为78。

技术优势支撑场景实现
高性能架构：FE（前端）与 BE（后端）分离设计，支持水平扩展，单集群可扩展至数百节点24。

多样化存储模型：支持明细表、聚合表、主键表，满足不同业务需求24。

实时数据导入：兼容 Kafka、Hadoop 等数据源，支持秒级数据可见67。

## 增删改查

doris的增删改查基本兼容mysql的语法，如果你是从MySQL迁移而来，对于基础语法将对你来说非常简单

当然，Doris（通常指 Apache Doris）与 MySQL 在查询语法上存在显著差异，尽管两者都支持标准 SQL 并努力兼容 MySQL 协议（Doris 前端兼容 MySQL 协议），但它们的底层架构、优化目标和适用场景（OLAP vs OLTP）决定了语法细节和功能支持的诸多不同。

以下是 Doris 和 MySQL 在查询语法上的主要差异：

1.  **核心差异根源：**
    *   **Doris：** MPP 架构的**分布式列式存储 OLAP 数据库**。设计目标是**海量数据的快速分析查询（Ad-hoc、报表、即席分析）**。强调**向量化执行、分区/分桶、物化视图、预聚合**。
    *   **MySQL：** 传统的关系型**行式存储 OLTP 数据库**。设计目标是**高并发的事务处理（增删改查）**。强调**ACID、索引优化、行锁**。

2.  **数据定义语言 (DDL) 差异：**
    *   **表引擎/存储模型：**
        *   **Doris:** 必须指定存储模型 (`ENGINE=olap`) 和关键属性：
            *   `DISTRIBUTED BY HASH(column) BUCKETS num`: **显式定义分桶方式和桶数量**。这是 Doris 实现并行计算和数据分布的核心机制。
            *   `PARTITION BY RANGE/RANGE/...`: 分区定义通常更显式，且对查询性能至关重要（分区剪裁）。
            *   支持多种数据模型：`AGGREGATE KEY`, `UNIQUE KEY`, `DUPLICATE KEY`。
        *   **MySQL:** 通常使用 `ENGINE=InnoDB` (或其他如 MyISAM)，没有分桶概念。分区 (`PARTITION BY`) 是可选的高级特性，主要用于数据管理而非核心性能依赖。
    *   **索引：**
        *   **Doris:** 索引类型较少。核心是**前缀索引**（自动基于前 36 字节），**Bloom Filter 索引**（用于高基数列的等值过滤），**Bitmap 索引**（用于低基数列的等值过滤）。不支持传统 B+树索引（如 MySQL 的二级索引）。创建索引的语法通常是 `INDEX index_name (column) USING BITMAP/BLOOM_FILTER`。
        *   **MySQL:** 支持丰富的索引类型：`PRIMARY KEY`, `UNIQUE KEY`, `INDEX` (B+Tree), `FULLTEXT`, `SPATIAL`。创建索引语法是标准的 `CREATE INDEX index_name ON table (column)` 或 `ALTER TABLE ADD INDEX`。

3.  **数据操作语言 (DQL/DML) 差异：**
    *   **JOIN 优化：**
        *   **Doris:** **强烈依赖查询优化器自动选择 Join 策略**（Broadcast Join, Shuffle Join/Partitioned Join, Colocate/Bucket Shuffle Join）。用户通常**不需要**（也不推荐）手动指定 `/*+ ... */` 提示（除非明确知道优化器选错）。`Colocate Join` 是 Doris 的重要特性，要求表的分桶方式和数量完全相同且 Join Key 是分桶列才能生效，性能最佳。
        *   **MySQL:** 优化器相对简单。用户有时需要手动指定 `STRAIGHT_JOIN` 或使用 `FORCE INDEX/USE INDEX` 提示来影响 Join 顺序或索引选择。
    *   **子查询：**
        *   **Doris:** 对**非相关子查询**支持良好，优化器通常能将其展开为高效的 Join。对**相关子查询**的支持相对有限，性能可能不佳，**强烈建议重写为 Join**。
        *   **MySQL:** 对相关和非相关子查询都有较好支持，优化器处理策略多样（物化、半连接转换等）。
    *   **窗口函数：**
        *   **Doris:** **全面支持标准的窗口函数** (`RANK`, `DENSE_RANK`, `ROW_NUMBER`, `LEAD`, `LAG`, `SUM/AVG OVER` 等)，这是其作为 OLAP 数据库的核心优势之一。
        *   **MySQL:** 从 8.0 版本开始才支持窗口函数。在 5.7 及之前版本不支持。
    *   **分组操作：**
        *   **Doris:** 支持 `GROUPING SETS`, `CUBE`, `ROLLUP` 进行多维聚合。支持 `WITH ROLLUP`。
        *   **MySQL:** 也支持 `GROUPING SETS`, `CUBE`, `ROLLUP` (8.0+) 和 `WITH ROLLUP`。
    *   **分页 (`LIMIT`/`OFFSET`):**
        *   **Doris:** `LIMIT` 后支持两个参数 `LIMIT offset, limit` 或 `LIMIT limit OFFSET offset`。**深分页 (`OFFSET` 值很大) 性能很差**，因为需要扫描并跳过大量数据。推荐使用更高效的方法（如记录上一页的最大值）。
        *   **MySQL:** 语法相同 (`LIMIT offset, limit` 或 `LIMIT limit OFFSET offset`)。深分页在 InnoDB 上性能也较差，但可能比 Doris 稍好（依赖索引）。
    *   **`ORDER BY` + `LIMIT`：**
        *   **Doris:** `ORDER BY col LIMIT n` **在没有索引的情况下，Doris 可以利用其 TOP-N 优化机制高效处理**（尤其是 n 较小时），避免全排序。
        *   **MySQL:** 严重依赖索引。如果 `ORDER BY` 的列没有索引，可能导致全表扫描和文件排序 (`Using filesort`)，性能差。
    *   **函数和操作符：**
        *   **Doris:** 提供大量**分析型函数**（窗口函数、多种聚合函数、位图函数、HLL 函数等）。部分字符串、日期函数的名称或行为可能与 MySQL 有细微差别。**类型转换通常更严格**。
        *   **MySQL:** 函数库更侧重于 OLTP 场景（字符串处理、日期操作、事务控制函数等）。类型转换通常更宽松（隐式转换）。
    *   **执行计划 (`EXPLAIN`):**
        *   **Doris:** `EXPLAIN` 输出反映分布式执行计划，包含 Fragment（执行阶段）、Exchange Node（数据交换）、OlapScanNode（扫描）、Aggregation Node（聚合）等。`EXPLAIN GRAPH` 提供可视化视图。对理解分布式查询如何执行至关重要。
        *   **MySQL:** `EXPLAIN` 输出显示单机执行计划，包含访问类型 (`type`)、使用的索引 (`key`)、扫描行数 (`rows`)、额外信息 (`Extra`) 等。

4.  **其他重要差异：**
    *   **事务支持：**
        *   **Doris:** 主要面向**分析型读负载**。写入通常是小批量导入（Stream Load, Insert Into）。支持**部分事务语义**（如导入任务的事务性保证），**不支持**跨多行或多表的复杂事务（如 MySQL 的 `BEGIN; ... COMMIT;`）。
        *   **MySQL:** 完整的 ACID 事务支持，是 OLTP 的核心。
    *   **并发控制：**
        *   **Doris:** 采用 MVCC (多版本并发控制) 处理读，写入通常涉及版本合并。并发写入能力不如 MySQL OLTP 场景。
        *   **MySQL (InnoDB):** 使用行锁和 MVCC 实现高并发读写。
    *   **数据导入：**
        *   **Doris:** 有多种高效的大规模数据导入方式：**Stream Load** (HTTP Push, CSV/JSON), **Broker Load** (通过 Broker 访问 HDFS/S3), **Routine Load** (持续消费 Kafka), **Insert Into** (小批量), **S3 Load** 等。这是 Doris 工作流的重要组成部分。
        *   **MySQL:** 主要使用 `LOAD DATA INFILE`, `INSERT INTO ... VALUES`, 或通过客户端工具（如 `mysqldump` 导入）。大规模导入效率通常低于 Doris 的专用机制。
    *   **视图：**
        *   **Doris:** 支持视图。物化视图是其强大功能，可自动透明加速查询，但创建和维护（自动刷新）有成本。
        *   **MySQL:** 支持视图。物化视图需要特定存储引擎（如 `CONNECT`）或手动实现（通过表和触发器），不如 Doris 原生支持强大和自动化。
    *   **处理 NULL 和空字符串：**
        *   **Doris:** **严格区分 `NULL` 和空字符串 (`''`)**。这是常见的一个迁移兼容点。
        *   **MySQL:** 行为取决于 SQL Mode。在默认模式下 (`' '`)，对于 `VARCHAR` 等类型，`NULL` 和空字符串 `''` **通常被允许共存，但比较时 `''` 不等于 `NULL`**。某些函数处理也可能不同。

**所以：**

1.  **基础 SQL 兼容性高：** 对于简单的 `SELECT ... FROM ... WHERE ... GROUP BY ... ORDER BY ... LIMIT` 查询，Doris 和 MySQL 语法非常相似，迁移成本低。
2.  **分布式特性是核心差异：** Doris 的 `DISTRIBUTED BY` (分桶)、`PARTITION BY`、`Colocate Join` 等是其发挥分布式性能的关键，MySQL 没有对应概念。**理解这些概念对 Doris 表设计和查询优化至关重要。**
3.  **分析功能强大：** Doris 在窗口函数、复杂聚合 (`GROUPING SETS/CUBE/ROLLUP`)、高效 TOP-N (`ORDER BY ... LIMIT`) 等方面作为 OLAP 数据库优势明显。
4.  **子查询与 JOIN 优化：** Doris 优化器擅长处理非相关子查询和自动选择 Join 策略，但对相关子查询支持较弱，建议改写为 Join。避免手动加提示，除非有确凿证据。
5.  **函数与类型：** 注意部分函数名称或行为的细微差异，以及 Doris 更严格的类型处理（尤其是 `NULL` vs `''`）。
6.  **避免深分页：** `LIMIT ... OFFSET` 在 Doris 中深分页性能极差，需设计替代方案。
7.  **`EXPLAIN` 是必备工具：** 在 Doris 中查看分布式执行计划 (`EXPLAIN` / `EXPLAIN GRAPH`) 是性能调优的基础。
8.  **明确场景：** 永远不要期望用 Doris 替代 MySQL 做高并发 OLTP。Doris 的核心价值在于 OLAP。

**迁移时重点检查：**

*   表定义中的分桶 (`DISTRIBUTED BY ... BUCKETS ...`) 是否合理设置。
*   复杂子查询（尤其是相关子查询）是否需要重写为 Join。
*   是否利用了窗口函数等分析特性。
*   深分页查询 (`OFFSET` 大) 的优化。
*   函数兼容性和 `NULL`/空字符串处理逻辑。
*   执行计划 (`EXPLAIN`) 是否高效（避免全表扫描，利用分区剪裁、分桶剪裁、物化视图等）。
