### 方案一：固定窗口计数方案（INCR + KEY过期）

#### **算法原理**

**时间窗口划分**：将时间轴划分为固定大小的窗口（如1秒），每个窗口独立计数。

**核心逻辑**：
1. 使用`INCR`命令记录当前窗口请求数
2. 窗口结束时自动重置计数（通过KEY过期实现）
3. 若计数超过阈值则触发限流

这是最直观的限流算法，也叫做**固定窗口计数器算法**。

#### **实现方式（Lua脚本示例）：**

```lua
local key = "limit:" .. KEYS[1] -- KEYS[1]是你传入的时间窗口，如 "20250827100101"
local limit = tonumber(ARGV[1]) -- ARGV[1]是阈值，如 100
local expire_time = ARGV[2] -- ARGV[2]是key的过期时间，可以设为2秒，保证窗口能过期

local current = redis.call('INCR', key)
if current == 1 then
    -- 如果是第一次设置这个key，同时设置它的过期时间
    redis.call('EXPIRE', key, expire_time)
end

if current > limit then
    return 0 -- 代表超出限流阈值
else
    return 1 -- 代表允许通过
end
```

#### **优点：**
1.  **极其简单**：逻辑清晰，非常容易理解和实现。
2.  **高性能**：只涉及Redis的一个`INCR`操作和可能的`EXPIRE`操作，对Redis的性能影响很小。
3.  **资源消耗低**：每个时间窗口只有一个key，内存占用非常少（虽然key多，但每个key都很小）。

#### **缺点：**

1.  **临界问题（突刺）**：这是固定窗口算法固有的缺点。假设你的限流是每秒100次，如果在窗口`20250827100101`的最后100ms来了100个请求，在窗口`20250827100102`的最初100ms又来了100个请求。**这意味着在200ms内通过了200个请求**，超过了系统设计的每秒100次的承受能力，可能压垮系统。
    

2.  **不够平滑**：流量可能在窗口开始时就被耗尽，导致窗口后期所有请求都被拒绝。

### 方案二：Redis Module - `redis-cell`

#### **算法原理**

**核心概念**：
- **令牌生成速率**：系统以恒定速率向桶中添加令牌
- **令牌桶容量**：桶可存储的最大令牌数
- **请求消耗令牌**：每个请求需要从桶中获取令牌
- **令牌不足限流**：无令牌可用时触发限流

`redis-cell`是一个Redis模块，它实现了**令牌桶算法**（Token Bucket），这是一种更高级、更平滑的限流算法。

#### **使用方法（CLI.THROTTLE 命令）：**
```bash
CL.THROTTLE my_user 100 3600 60 1
```
这个命令的意思是：
- `my_user`：限流标识
- `100`：令牌桶容量（max_burst）
- `3600`：令牌生成速率（每60秒生成3600个令牌 = 每秒60个）
- `60`：时间窗口（秒）
- `1`：本次申请令牌数

CL.THROTTLE命令完整语法：

```bash
CL.THROTTLE <key> <max_burst> <tokens_per_period> <period> [apply]
```

参数说明：
- `<key>`：限流标识（用户ID/API路径等）
- `<max_burst>`：最大突发容量（令牌桶大小）
- `<tokens_per_period>`：周期内生成令牌数
- `<period>`：周期长度（秒）
- `[apply]`：本次申请令牌数（默认1）

返回值解析：

```bash
127.0.0.1:6379> CL.THROTTLE user100 10 30 60
1) (integer) 0       # 0=允许，1=拒绝
2) (integer) 10      # 令牌桶容量
3) (integer) 9       # 当前剩余令牌
4) (integer) -1      # 拒绝时需等待秒数，允许时为-1
5) (integer) 2       # 令牌桶填满还需秒数
```

#### **优点：**
1.  **应对突发流量**：令牌桶算法允许流量有一定程度的突发。如果桶里有积攒的令牌，瞬间的请求可以快速得到处理，然后再平滑到正常速率。这更符合实际业务场景。
2.  **解决临界问题**：由于令牌是匀速添加的，而不是在窗口重置时瞬间补满，因此可以有效避免固定窗口算法的临界突刺问题。
3.  **功能强大**：一个命令返回的结果非常丰富，通常包含：
    *   是否成功（0/1）
    *   桶的总容量
    *   剩余令牌数
    *   下次重试需要等待的时间（秒）
    *   桶被完全填满所需的时间（秒）
    这些信息对客户端非常友好，可以据此告诉用户“需要等待多少秒后重试”。

#### **缺点：**
1.  **依赖额外模块**：需要确保你的Redis服务器已经加载了`redis-cell`模块。这在自建Redis时增加了一个部署步骤，但在云服务商（如AWS ElastiCache、阿里云Redis）的高版本中通常已预装。
2.  **稍复杂**：理解和配置令牌桶的**容量（burst）** 和**速率（rate）** 两个参数需要多一点思考。
3.  **性能**：虽然依然非常快，但其内部逻辑比简单的`INCR`要复杂一些。

### 对比与选择建议

| 特性 | 固定窗口方案 | redis-cell (令牌桶) |
| :--- | :--- | :--- |
| **实现复杂度** | 低（自己写Lua） | 低（使用现成命令） |
| **平滑度** | 低，有临界问题 | **高**，流量平滑 |
| **突发处理** | 不支持 | **支持** |
| **额外依赖** | 无 | 需要Redis加载该模块 |
| **功能信息** | 简单（通过/不通过） | **丰富**（剩余令牌、等待时间） |
| **内存占用** | 每个窗口一个key | 每个限流主体一个key |
| **单请求执行效率** | **极高** (纳秒级) | **很高** (稍多纳秒) |
| **内存压力** | **高** (海量临时Key) | **低** (少量固定Key) |
| **CPU压力** | **极低** | **低** |
| **网络压力** | 低 | 低 |
| **功能表现** | 差 (有临界突刺) | **优秀** (平滑限流) | 


**如何选择：**

1.  **选择固定窗口方案，如果：**
    *   你的业务对**严格的“每秒多少次”** 要求不敏感，或者临界时的少量超载系统可以承受。
    *   你想要最简单、依赖最少、性能最高的方案。
    *   你的Redis环境无法安装第三方模块。

2.  **选择`redis-cell`令牌桶方案，如果：**
    *   你希望流量更加**平滑**，避免突刺对下游系统造成冲击。
    *   你的业务有**突发流量**的场景（例如：用户抢券、定时任务启动），并希望系统能合理应对。
    *   你希望客户端能获得更详细的限流信息（如重试等待时间）。
    *   你的Redis环境（或云服务商）已经支持了`redis-cell`模块。

3. **考虑另一种折中方案：滑动窗口**
    你可以实现一个**滑动窗口日志算法**，它比固定窗口更平滑，但比令牌桶简单。不过它在Redis中的实现成本比你现在的方案高很多（需要使用ZSET和多个命令），性能也更低。这里简单提一下，以供你调研：
    *   **原理**：用一个ZSET存储请求的时间戳。每次请求时，删除所有超过1秒前的旧时间戳，然后计算当前ZSET的大小是否小于100。如果是则允许请求并记录当前时间戳。
